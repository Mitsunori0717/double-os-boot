# 技術解説 — なぜこの設計なのか

## 1. 要件の整理

| 要件 | 備考 |
|---|---|
| C: に物理 Windows、D: (別ディスク) に物理 Linux | 仮想ディスク不可 |
| 2 つの OS を **同時に** 起動 | 排他起動のデュアルブートでは不可 |
| モニター 2 枚にそれぞれの OS を表示 | 画面転送 (RDP 等) ではなくネイティブ描画が望ましい |
| データのやりとり | 双方向 |
| **問題切り分けができること** | ソフトの不具合が Windows / 仲介層 / ソフト自体のどれに起因するか判別可能であること |

## 2. 物理的な制約 — なぜ「完全に仲介なしの同時起動」は存在しないのか

x86 アーキテクチャでは、以下の資源の支配権を持てる OS は同時に 1 つだけです。

- **CPU の特権モード (ring 0 / VMX root)**: ページテーブルの根 (CR3)、割り込み記述子表 (IDT)、
  モデル固有レジスタ (MSR) は CPU 1 コアにつき 1 系統しかない
- **MMU / 物理メモリマップ**: 2 つの OS が互いを知らずに同じ物理メモリを管理すれば即座に破壊し合う
- **割り込みコントローラ (APIC)・タイマー**: デバイスからの割り込みの配送先は 1 つ

したがって「2 つの汎用 OS を 1 台で同時に動かす」には、資源の割り当てを決める層が
**必ず** 1 つ存在します。選択肢は次の 3 つしかありません:

1. **どちらかの OS 自身がその層を兼ねる** (Hyper-V / WSL2 / VirtualBox など)
2. **独立した薄い層を置き、ハードウェアは各 OS に直接割り当てる** ← 本システム (KVM + VFIO)
3. **物理的に 2 台にする** (これのみ真の無仲介。ただし「1 台の PC」という前提から外れる)

## 3. 本システムの設計: ハードウェア分割 (静的パーティショニング)

「仲介層をゼロにできない」なら、次善は **仲介層が touching するハードウェアを最小にする** ことです。
本システムでは各資源を次のように割り当てます。

| 資源 | 割り当て方式 | 仲介層の関与 |
|---|---|---|
| GPU (モニター1) | VFIO による PCI パススルー。Windows の純正ドライバが実 GPU の MMIO/割り込みを直接制御 | IOMMU の DMA アドレス変換のみ (ハードウェア機能) |
| C: ディスク | 物理ディスク全体をブロックデバイスとして専有 | I/O リクエストの受け渡しのみ |
| USB | コントローラごと PCI パススルー (任意) | なし (DMA 変換のみ) |
| CPU コア | ピンニングで物理的に分割。VT-x により Windows のコードは CPU 上で直接実行 | VM Exit 時のみ介入 |
| メモリ | HugePages で起動時に固定確保。EPT (ハードウェアページテーブル) で変換 | なし (ハードウェア機能) |
| NIC | 仮想 NIC (ここだけ準仮想化。必要なら NIC もパススルー可能) | あり |

つまり Windows から見えるハードウェアのうち、**GPU・ディスク・USB・CPU 命令実行は「本物」** です。
エミュレートされているのはマザーボード的な足回り (チップセット、ファームウェア、NIC) だけです。

### 画面出力について

Windows 専有 GPU の映像出力端子にモニター1 を物理接続します。
描画は GPU が行い、映像は GPU から DisplayPort/HDMI で直接出ます。
**画面転送 (RDP/VNC/SPICE) は一切使いません**。遅延・画質・リフレッシュレートはネイティブと同一です。

## 4. 問題切り分けの設計

本設計の最重要ポイントは、**同一の物理 Windows インストールが 2 つのモードで起動できる** ことです。

```
                 ┌──────────────────────┐
                 │  C: の物理 Windows    │ ← ディスク上の実体は 1 つだけ
                 └──────┬───────┬───────┘
        GRUB から選択     │       │   Linux 上から起動
     (仮想化レイヤーなし)  │       │  (KVM/VFIO 調停あり)
                 ┌──────▼──┐ ┌──▼──────────┐
                 │ ネイティブ │ │ 同時起動モード │
                 └─────────┘ └─────────────┘
```

切り分けアルゴリズム:

1. 同時起動モードでソフトに問題が発生
2. 再起動し、GRUB から同じ Windows をネイティブ起動して再現手順を実行
3. - **再現する** → 仲介層は物理的に存在しない状態なので、Windows かソフト自体の問題と確定。
     以降は通常の Windows トラブルシューティング (イベントビューア、セーフモード等) に進める
   - **再現しない** → 差分は仲介層のみなので、KVM/VFIO 起因と確定。
     TROUBLESHOOTING.md の該当節 (MSI 割り込み、Hyper-V enlightenment、電源管理) を確認

この 2 モード性により、「どの層の問題か分からない」状態が原理的に発生しません。
また、確実性が最優先の作業 (業務・本番環境・アンチチートゲーム) は常にネイティブ側で行えます。

## 5. 検討して不採用にした案

| 案 | 不採用理由 |
|---|---|
| Hyper-V 上に Linux (当初案) | Linux 画面が RDP 転送になる。GPU 専有不可。ホスト Windows 側にも Hyper-V 層が常駐し、切り分け要件に反する (alternatives/hyperv/ に参考として残置) |
| WSL2 | 同上に加え、Linux が物理ディスクの独立インストールにならない |
| coLinux 系 (協調カーネル) | 開発停止・64bit 非対応・Windows 11 で動作不能 |
| Jailhouse 等の静的パーティショニング HV | 思想は理想的だが Windows ゲスト非対応 |
| 2 台の PC + KVM スイッチ | 真の無仲介だが「1 台の PC」の前提外。予算が許すならこれが最も堅牢 (README 制約節参照) |

## 6. 性能の目安

| 項目 | ネイティブ比 (一般的な実測値) |
|---|---|
| CPU | 96〜99% (ピンニング + HugePages 時) |
| GPU (3D) | 95〜99% (パススルーのため GPU 自体はフルスピード) |
| ディスク | 90〜98% (物理ディスク直接・cache=none/io=native 時) |
| 入力遅延 | evdev パススルーでほぼ知覚不能。厳密を求めるなら USB コントローラごと専有 |
